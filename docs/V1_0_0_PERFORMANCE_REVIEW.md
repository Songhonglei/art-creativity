# v1.0.0 性能审查与优化方案

日期：2026-11-10。基线：`eac2545`，应用代码 `8913d2c`。状态：**分析完成，优化待实施**。本轮只增加文档、临时诊断和证据；没有修改游戏实现、字体资产、正式产物或版本。

综合问题清单见[审查待办](V1_0_0_REVIEW_BACKLOG.md)。性能项使用PFR编号；与R03/R07/O01等关联的事项不重复计算为独立缺陷。

## 结论与实施顺序

优先处理场景绘制、画质分级、街区生成和暂停时的无效工作；随后处理界面更新及宠物寻路缓存。资源体积可以作为独立的一批优化。现有证据不支持“移动端性能已经达标”，也没有证明新的主角模型是主要瓶颈。

1. 第一批：PFR01/PFR02/PFR03，降低场景和阴影负担，为流畅档提供稳定预算。
2. 第二批：PFR04/PFR05/PFR06，按需更新界面与暂停画面，缓存宠物路径。
3. 独立批次：PFR07，精简字体与图片，逐页核对字形和观感。
4. 发布前：PFR08/PFR09，完成长时、前后台、原生存储及真机测量；修复R03/R07。

## 测量环境与有效边界

- 当前H5生产包通过独立临时origin `127.0.0.1:5217`读取；先确认该origin没有存档，再写入专用测试数据。结束时仅删除本轮两个测试key，关闭任务空间和临时服务器。既有试玩origin与用户存档未修改。
- 设备是Apple M1 Pro、桌面Chrome156，实际GPU为ANGLE Metal；游戏快照使用390×844、DPR1模拟视口。它不是Android/iOS，也不是手机GPU/CPU或触控性能测试。
- 测试角色为10级女性、申城守望、战术棍、柴犬；三个位置为营地(-18,31.2)、核心城区(0,20)、外城(144,144)。这是偏重的角色配置，不能代表新玩家平均值。
- [9个渲染快照](evidence/v1.0.0-performance-review/render-inspection.json)记录流畅/均衡/高画质的绘制调用、三角形和实际碰撞体。三个RAF用于确认画面更新，不是稳定帧率采样；人物/街敌状态随运行略有不同，不将这些快照当作精确跨画质A/B结果。
- 本轮RAF出现约1秒调度间隔，首个含120帧采样的探针在等待RAF时超过工具15秒上限，未形成完整结果。页面可见/有焦点也未排除宿主节流。因此保留原始短样本，**不输出本轮FPS/p95游戏帧率结论**，不筛掉慢帧凑达标结果。
- 历史[相同路线结果](evidence/v1.0.0/performance-final.json)的v1 p95为41.7/42.1ms，仅是M1 Pro、1024×768流畅档、关闭simulation tick后的短渲染对比，不能证明完整玩法或手机30fps。
- CPU微基准与整局帧率分开：Node函数计时使用真实生产碰撞体；街区计时使用静态HTML页，真实Canvas2D与Three几何，运行三轮，排除游戏RAF/渲染并发。它们均不包含真机、GPU上传或完整玩法。

## PFR01 场景与高画质阴影负担

**优先级高；已观察到渲染负担，手机影响待测；成本中。**

当前390视口快照：

| 画质 | 营地调用/三角形 | 核心城区调用/三角形 | 外城调用/三角形 |
| --- | ---: | ---: | ---: |
| 流畅 | 172 / 110378 | 211 / 107264 | 92 / 81778 |
| 均衡 | 169 / 113166 | 227 / 113388 | 128 / 98006 |
| 高 | 385 / 178758 | 503 / 196968 | 351 / 175942 |

调用数来自renderer.info，**高画质包含阴影额外pass**；不能把三角形数等同于模型资产面数。主角既有预算为最多17416三角形/39次调用，场景其余部分仍值得优先分析。

源码：`engine.ts`的renderer/shadow设置；`world.ts:createTrees/createSkyline/createLandmarks`。树按单棵合批，核心建筑部分按全城材质合为大mesh，缺少按街区的可见性/距离分级。

建议：

- 重复树木、路灯和街道构件按街区与材质做实例化或批处理，同时保留局部包围盒；避免把整座城合成无法有效裁剪的大mesh。
- 远处建筑/树木采用简化轮廓，细节优先留给近景、主角及战斗目标。
- 高画质缩小投影者范围，按距离/对象选择阴影；评估1024阴影与当前2048的实际观感，设置合理的阴影更新策略。

验收：在相同机型、存档、镜头、路线和画质下记录调用、GPU/CPU时间与p95；第一批以核心城区调用降低至少25%为建议目标，阴影/地标/血条/角色穿模和碰撞均不得回归。最终手机帧率需真机确认。

## PFR02 街区生成与首屏初始化同步占主线程

**优先级高；结构风险已确认，隔离计时已完成；成本中。**

`streaming.ts:update/load`每帧最多生成两块，但一次load内部同步创建大量几何、合并、计算地形和注册碰撞，没有毫秒预算。`World`构造也同步完成地形、贴图、树、建筑与首批街区。

[静态页面三轮计时](evidence/v1.0.0-performance-review/streaming-isolated.json)：

- 单块中位耗时约1.2–2.5ms；一次最多两块的update耗时峰值为流畅10.1ms、均衡12.7ms、高5.1ms。
- 单步跨区update为2.3–3.6ms；Streamer构造（含真实Canvas贴图）11.4–24.2ms。
- 上述仅是桌面CPU生成过程，不含GPU上传、shader编译、核心城区初始化或完整玩法；不能据此承诺手机预算。
- [游戏运行中的初探](evidence/v1.0.0-performance-review/streaming-microbench.json)曾出现数百毫秒wall time，与隔离结果不一致，受到运行负载/调度干扰。保留原文，不将其作为“游戏必现数百毫秒卡顿”的证据。

建议：按每帧约2–4ms的建议生成预算分阶段执行，缓存可复用基础几何和材质；优先当前路径、再补远景。碰撞的逻辑数据要先到位，延迟美术生成不能让人物穿墙或落入未加载区域。初始化按阶段让出主线程，加载进度跟随真实步骤；先评估现有平台允许的实现，不默认增加Worker或新的高消耗能力。

验收：持续走过多次街区边界，采集生成/上传耗时、长任务和p95；旧区域回收与折返后布局一致，不能用QA瞬移一次加载所有块的耗时代替正常移动结果。

## PFR03 流畅档降级范围有限、缺少自适应

**优先级高；源码已确认；成本中。**

- 核心地形固定120×120网格（28800三角形），水面64×88网格（11264三角形），各画质共用；核心树木与建筑没有相应LOD。当前流畅档主要降低像素比、草、粒子和外围半径。
- 外围半径1/2分别对应最多9/25块；均衡档的碰撞与场景工作量较高。当前捕获碰撞体最多380个圆形＋129个方形，移动/镜头等仍会遍历这些集合；是否值得空间索引需CPU profile继续确认。
- `DistrictStreamer.setQuality`改变后续detail和半径，但仍位于目标范围内的已加载chunk不重建，因而其中树木/灯具可能仍保持旧细节。
- 像素比上限为流畅0.8、均衡1、高1.5；高DPR手机在高画质下最多是均衡的2.25倍像素量，此外还有阴影。当前只有软件渲染器检测，没有根据持续帧耗时自动调整。

建议：分离核心/远景LOD和阴影等级；切换画质后让存量chunk逐步更新。增加有滞回的降级策略和用户覆盖选项，避免反复跳档。地形简化时保留河岸和桥面的采样精度，并同步核对groundHeight与真实视觉表面。

验收：同一地点切换高→流畅→高即能观察到约定细节变化；不需离开再回来。高DPR/中档Android与iOS设备记录缓慢转镜头、战斗及雨天结果，验证预算与温升。

## PFR04 HUD和DOM存在重复更新

**优先级中；源码确认，成本占比未定量；成本低至中。**

`Engine.publish`约每100ms构造完整Snapshot并交给App；Snapshot每次复制成长/资源等，WorldMap也随之重建元素。`updateMarkers`每次渲染重复设置display、transform、文字及血条属性，即使某些值未变化。

建议：按状态变化写DOM，位置与数字分开；静态菜单/地图图层与高频气血/罗盘更新分开，按需memo，而非给整个UI提高频率。保持战斗反馈及时，地图可采用更低的独立刷新率。先profile再决定是否需要空间查询或更换状态管理，不引入无必要的新依赖。

验收：记录普通巡逻、交战、静止菜单的React提交次数、DOM写入和主线程时间；血条、锁定、冷却、保存错误和读屏状态不能延迟或漏更新。

## PFR05 暂停菜单仍重复绘制整座场景

**优先级中；源码确认；成本低至中。**

`engine.ts:loop`暂停后约每0.15秒仍执行world/角色更新、render、marker及Snapshot发布；菜单遮盖时画面静止，但仍有GPU和DOM工作。按需绘制的HeroPreview/PetPreview已有可保留的基础。

建议：稳定暂停状态只在首次进入、尺寸/画质/模型变化时重绘主canvas；死亡、起身、正在播放的预览动作等保留必要帧。音频策略与画面刷新分开处理。

验收：静态菜单保持30秒，主场景render调用停止或达到约定极低频；菜单、设置、死亡过程、WebGL恢复和试衣动作仍正常。真机测前后台耗电/温升，不能以浏览器短测试替代。

## PFR06 宠物跟随遇障碍时每帧重算路径

**优先级中；关联O01；成本中。**

`collision.ts:followPet`在直线被挡时每帧重建角点可视图与搜索。独立的柴犬引路已按约1秒刷新，不应混为同一函数。

[Node计时](evidence/v1.0.0-performance-review/cpu-microbench.json)使用9组实际碰撞体，每组60次：自然跟随p95约0.017–0.158ms；围绕真实障碍构造的绕行位置p95约0.132–0.500ms。数据支持缓存能减少工作，**不支持把它认定为当前头号卡顿原因**。Node速度也不等同于手机速度。

建议：缓存路线及下一路点，目标明显移动、路线受阻或碰撞区版本变化再重算；限制重算频率，直线可达时直接跟随。dt=0暂停状态无需重新寻路。

验收：同一条有拐角路线比较重算次数、CPU与p95；不穿墙、不震荡、不卡角，回营/复活/区域卸载后能重新跟上。

## PFR07 字体与图片是包体优化重点

**优先级中；体积已核算；成本低至中。**

[ZIP分析](evidence/v1.0.0-performance-review/package-analysis.json)：总包3107490字节；压缩payload约3098774字节。

| 内容 | ZIP内压缩字节 | 占payload |
| --- | ---: | ---: |
| 全部字体 | 1949942 | 62.9% |
| 24张主角图片 | 767392 | 24.8% |
| 脚本、样式及其他 | 381440 | 12.3% |

正文中文与宋体两份合计原始1480860字节，约占整个ZIP48%。[临时字体子集估算](evidence/v1.0.0-performance-review/font-subset-estimate.json)保留当前源码字符及ASCII，将两份字体从各2406码点缩为1092码点：642204→280296字节、838656→362800字节，合计减少837764字节（约818KiB），当前源码中原有覆盖字符未丢失。

这是分析用临时文件，**没有替换应用字体，也没有完成逐页视觉/授权命名验收**。只做这两份子集，ZIP估算约2.16MiB，仍可能超过2MiB建议值，正式数值必须重新打包审计。标题A保持已批准轮廓。后续核对宋体/多份英文字体的实际依赖，头像/缩略图按显示尺寸及DPR导出，保留主体细节；不要先假设某字体完全没用或随意删掉回退字形。

验收：所有菜单、战斗、模型名、区域名、动态数值和异常提示无缺字，正文与标题排版符合批准稿；H5/IIFE无新增外网请求，许可保留，ZIP内容审计和体积重新计算。

## PFR08 内存与缓存预算需要长时验证

**优先级中；R07是已复现残留，其余为待测预算；成本中。**

已有措施：街区离开半径后回收几何/碰撞，布局缓存上限256，主角模型缓存上限2；之前12次衣橱开关GPU几何221→221、纹理23→23，没有该流程持续增长证据。

需要补测：宠物缓存最多12种外观，主目标最多7种，街敌按3槽×6种最多18个模型；它们有界，但“有界”不代表适合手机内存。当前高画质三位置快照几何计数由298增至509，可能含首次上传、阴影可见物与有界模型缓存，不能直接认定泄漏。

建议：为模型/贴图设资源预算并记录峰值；必要时对宠物/街敌使用小型LRU或模型池。先修R07通知计时残留。保留既有噪声buffer复用、预览按需渲染及资源释放，不为优化破坏有效措施。

验收：真机连续20–30分钟巡逻、反复跨区/折返、切宠/换装/开关预览，观察稳定后的内存与GPU资源平台；长时无持续线性增长、上下文频繁丢失或异常温升。

## PFR09 存档计算开销轻，原生IO与队列待测

**性能优化优先级低；可靠性R01/R02/R03优先。**

隔离样本普通存档2648字节，填满2048个防重奖励id后30209字节。Node中JSON序列化p95约0.009/0.073ms，Snapshot约0.013ms以内，未包含localStorage/native IO。这不能证明实际宿主写入便宜，但目前计算侧证据支持保留约2秒检查点，优先处理R03待写合并、错误和挂起恢复。

验收：实际小红书宿主测p50/p95原生读写延迟、后台/关闭时最后一份进度和慢写队列；不能用压缩JSON代替异常存档保护。

## 建议验收口径

- Android/iOS各至少一台，以记录机型的中档设备为主；H5和小红书实际容器分别验收。
- 相同路线含核心城区、外城跨区、三敌交战、雨天、宠物绕障碍、死亡恢复、菜单与3D预览。
- 建议手机稳定30fps目标：记录中位、p95、>50ms帧占比和长任务；明确机型、画质、DPR、温度、前后台和样本时长后冻结预算。当前未宣称达标。
- 将CPU生成、simulation、寻路、DOM/React、GPU绘制与存储分别计时，避免把浏览器节流、QA瞬移或GC全归因于某个功能。
- 这轮只有文档/诊断变化，未重复构建或运行玩法测试；上一轮228项测试与TypeScript检查通过仍是历史记录，不冒充本轮新增通过。
